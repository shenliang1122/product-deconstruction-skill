# Agent、Workflow、工具与运行实例的证明门槛

当分析对象包含 Agent、Multi-Agent、工具调用、上下文、模型路由或工作流时读取本参考。

## 1. 先做实体分类

不要把页面上所有拟人名称都叫 Agent。对每个组件先分类：

| 类型 | 判定依据 | 可以证明什么 | 常见误判 |
|---|---|---|---|
| UI Persona | 名称、头像、对话身份 | 用户看到一个角色化界面 | 不证明独立运行或独立上下文 |
| Workflow Stage | 有顺序、状态和交付节点 | 工作流阶段存在 | 阶段不一定由独立 Agent 执行 |
| Agent Role | 官方或代码定义职责与输入输出 | 架构上存在角色职责 | 不证明本次创建了实例 |
| Runtime Agent Instance | 有 run/subtask ID、独立状态、上下文或日志 | 本次确有独立执行单元 | 不能只靠复数文案或进度卡片 |
| Tool/Service | 有调用上下文、参数、结果或状态写入 | 存在可调用能力边界 | 工具不等于 Agent |
| Model | 有模型/版本或配置证据 | 可见模型配置或调用 | 模型名称不等于动态路由 |

## 2. Multi-Agent 证明阶梯

每项结论使用达到的最高证据等级，不跨级外推：

1. **L1：界面命名。** 页面显示多个角色/工种/阶段。只能证明 UI 表达。
2. **L2：官方能力声明。** 官方文档描述主 Agent、子 Agent 或并行架构。只能证明公开设计口径。
3. **L3：本次运行记录。** 当前任务出现多个子任务/Agent 实例、独立状态或独立结果。
4. **L4：独立执行证据。** 每个实例有稳定 ID、独立上下文/环境、工具调用、开始结束状态和父子关系。
5. **L5：代码或完整追踪。** 编排、消息传递、状态存储、重试和汇总逻辑可以在代码/trace 中复现。

报告中写明当前达到的等级。例如：

```text
产品公开架构达到 L2；本次运行只有单一身份和阶段投影，未达到 L3。
因此可以描述“产品声称支持 Multi-Agent”，不能描述“本次由多个 Agent 并行完成”。
```

## 3. 单个 Agent 契约

只有证据支持时才填写：

| 字段 | 要回答的问题 |
|---|---|
| 身份 | UI Persona、角色定义还是运行实例？ |
| 触发 | 用户动作、状态条件、编排调度还是定时事件？ |
| 输入 | 用户请求、全局上下文、上游资产、权限、预算 |
| 判断 | 可观察规则或公开计划；不要声称隐藏推理 |
| 工具 | 工具名/边界、参数、权限、结果、失败状态 |
| 写入 | 哪个状态、文件、资产或外部系统被修改 |
| 输出 | 给用户、主 Agent 或下游 Agent 的内容 |
| 确认门 | 执行前、阶段间或交付后的人工确认 |
| 错误/恢复 | 重试、回退、检查点、幂等、部分成功 |
| 完成 | 哪些可验证条件共同成立 |
| 证据等级 | E/O/A/R/G/C 及证明阶梯等级 |

证据不足时可以写“职责单元”或“阶段”，不要为了对齐框架创造 Agent 名称。

## 4. 主 Agent 与子 Agent

检查：

- 主 Agent 如何判断是否拆分；
- 子任务是否同构、互斥、可独立完成；
- 子 Agent 是否共享上下文、文件或账号权限；
- 子 Agent 是否互相通信；
- 父子任务如何关联稳定 ID；
- 子结果如何验收、去重、冲突处理和汇总；
- 单个子任务失败时整体是 Failed、Partial 还是继续；
- 并发、预算和速率限制如何影响调度；
- 用户能否查看、停止、重跑单个子任务。

若只有官方文档，以上均按官方声明记录；当前任务行为仍需 L3+ 证据。

## 5. 工具证明门槛

工具分析至少区分：

1. **动作摘要可见：** 只证明产品展示了某类动作。
2. **参数可见：** 可以分析输入契约和权限范围。
3. **结果可见：** 可以验证成功/失败与数据写入。
4. **状态关联：** 有 call ID、run ID、幂等键或资产引用。
5. **失败样本：** 才能描述重试、退避、退款和恢复的实际机制。

页面显示“读取网页”不能确定其使用云浏览器、HTTP 抓取、搜索 API 还是连接器。用“所需能力 / 可选实现 / 仍未知”表达。

## 6. 上下文与数据流

把“上下文”拆成可观察对象：

- 原始用户请求；
- 系统/项目约束；
- 计划与任务状态；
- 来源和工具结果；
- 中间文件/外部记忆；
- 资产稳定引用；
- Agent 间消息或交接；
- 用户确认与修订；
- 预算、权限和安全策略。

对每个对象记录生产者、消费者、读写时机、引用方式、版本和证据。文件名出现只证明对象被展示；文件内容、版本和下游读取需要额外证据。

## 7. 模型路由

以下信号分别处理：

- 模型选择器：证明用户可以选择或看到配置；
- 单一模型名：证明当前 UI 暴露的运行配置；
- 官方“自动选择最佳模型”：属于 `O##`；
- 运行记录中的模型切换：才证明某次动态路由；
- 失败后的模型切换/降级事件：才证明降级策略实际发生。

不要从输出风格猜模型供应商，也不要从 Agent 数量推断模型数量。

## 8. Agent 架构图规则

- As-Is 图中用不同视觉样式区分 E、O、R、G；
- 官方能力架构与当前运行架构分开画，或明确使用两条泳道；
- 每个 Agent 节点标明它是角色还是运行实例；
- 每条调用线标明触发条件、数据/资产和证据编号；
- 失败、取消和回退只有真实样本时画成现状；否则放 To-Be；
- 不把公开计划摘要画成隐藏 CoT；
- 不把“阶段 1–4”自动画成“Agent 1–4”。

## 9. 完成检查

- 已声明 Multi-Agent 证明等级；
- 产品能力与本次运行没有混写；
- UI Persona、Stage、Role、Instance、Tool、Model 已分类；
- 每个 Agent/职责单元有输入、输出、状态和证据边界；
- 工具参数、结果、错误和重试没有超出可见证据；
- 上下文对象有生产者—消费者关系；
- 模型路由只在运行证据存在时写成事实；
- As-Is 与建议的检查点、评估器、路由和降级严格分离。
