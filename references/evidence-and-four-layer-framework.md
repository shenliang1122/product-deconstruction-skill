# 证据门槛与四层拆解框架

每次产品拆解都必须读取本参考资料。

## 1. 证据门槛

### 一手证据

可接受的一手证据包括：

- 按时间顺序排列，能够显示控件、消息、状态、资产、错误和结果的完整页面截图或录屏；
- 已获用户授权、可以只读检查的产品网址；
- 原始源代码及相关配置；
- 导出的消息、项目数据、任务记录、日志或资产元数据；
- 来源可见的生成结果文件；
- 与观察行为直接对应的官方文档。

以前的分析总结、文件名、图片说明、营销文案和个人记忆都属于二手证据。它们只能用于定位一手证据，不能单独用于确认事实。

### 先区分结论对象

同一条证据对不同对象的证明力不同。拆解开始前先选择对象层级：

| 对象层级 | 典型问题 | 不能外推到 |
|---|---|---|
| 整个产品 | 产品定位、能力组合、商业模式 | 所有账号、地区和每次运行都相同 |
| 某项功能 | 功能入口、规则、能力边界 | 整个产品只有这一种工作方式 |
| 一次运行 | 这次输入、执行、状态与结果 | 产品长期稳定性或普遍成功率 |
| 单个 Agent/职责单元 | 触发、输入、工具、输出、交接 | 一定是独立运行实例 |
| 工具/数据流 | 调用、写入、引用、版本 | 上层用户体验或整体架构 |

结论必须带适用对象。产品官方文档可以证明“公开能力口径”，不能替代“一次运行”的 trace；单次成功资产不能证明产品级可靠性。

### 证据来源角色

| 编号 | 标签 | 证明范围 | 不能自动证明 |
|---|---|---|---|
| `E##` | `【页面/代码事实】` | 当前界面、代码、日志或运行直接可见 | 不可见后端与长期稳定性 |
| `O##` | `【官方公开】` | 官网/文档在访问时的公开口径 | 当前运行确实触发、厂商自报已独立验证 |
| `A##` | `【资产事实】` | 文件存在、格式、字段和可检查内容 | 内容正确、UI 已完成、来源已核验 |
| `R##` | `【合理推断】` | 对 E/O/A 的最小解释 | 私有实现唯一如此 |
| `C##` | `【证据冲突】` | 多信号不一致 | 哪个不可见系统一定故障 |
| `G##` | `【尚未确认】` | 明确缺口和待补证据 | 不能用建议填充现状 |
| `M##` | 方法/框架来源 | 报告组织、问题与评分格式 | 目标产品事实、示例结论或分数 |

生成报告本身可以作为 `A##` 证明资产存在。其引用链接只有被独立打开核验后，才可另建 `O##` 或其他直接证据。

### 证据就绪度维度

使用定性判断，不使用数字评分：

| 维度 | 达到就绪的条件 | 常见缺口 |
|---|---|---|
| 范围 | 目标产品/功能/Agent 及期望深度明确 | 产品名仍是占位符，或只说“全部分析” |
| 覆盖 | 入口、主流程、决策、结果和至少一次状态变化可见 | 只有宣传首页或一张孤立的最终结果截图 |
| 时间顺序 | 可以从最早到最晚还原过程 | 截图没有顺序，或缺少中间状态 |
| 可读性 | 页面原文、控件、资产和错误能够辨认 | 截图被裁剪、模糊或只有缩略图 |
| 结果验证 | 可以在界面、资产或代码中核对产品声称的输出 | Agent 说“完成”，但没有结果承载界面 |
| 状态覆盖 | 聊天、画布、任务、资产、预览或同类状态界面可见 | 多界面工作流只展示了其中一个界面 |
| 来源 | 证据来源、时间或顺序已知 | 文件被重命名，且文件名与内容冲突 |

### 门槛判断

- **不充分：** 没有一手证据、证据不可读或目标不明确。索取缺失证据并停止。
- **部分充分：** 足以回答一个有限问题，但不足以还原完整架构。只分析被支持的范围，并先列出证据缺口。
- **充分：** 足以追踪用户输入、系统判断、执行、输出和状态变化，覆盖当前请求范围。

证据是否充分取决于问题本身。一张截图可以证明某个按钮的名称，但不能证明完整端到端旅程。

### 不同分析模式的最低证据要求

| 模式 | 最低证据 |
|---|---|
| 用户旅程 | 最早输入、所有可见确认/选择步骤、最终结果、失败界面或证据缺口 |
| 单个 Agent | 每次可见出现、触发条件、输入、公开计划、工具/结果痕迹、输出、确认和下游交接 |
| 工具契约 | 调用上下文、参数或选项、成功结果、状态写入；失败和重试只能在真实发生时分析 |
| 架构拆解 | 用户旅程 + Agent/工具/上下文证据 + 模型/配置界面 + 资产/状态/错误界面 |
| 源代码拆解 | 程序入口、核心领域模块、数据模型、外部集成、配置，以及相关测试或日志 |
| Multi-Agent 运行 | 至少有本次任务的多个运行实例/子任务、独立状态或结果；只有官方说明时只能分析公开设计 |
| 外部框架重构 | 完整框架或可定位章节 + 目标产品证据；框架只作为 `M##` |
| 评分 | 每个评分维度都有样本、最低证据、权重和对应编号；未知维度不得评分 |

## 2. 证据纪律

统一使用来源标签与判断标签：

- `【页面/代码事实】`——可以直接看到或复现。
- `【官方公开】`——官方公开口径，记录访问时间；不自动证明当前运行。
- `【资产事实】`——资产存在及可检查属性；不自动证明内容正确。
- `【合理推断】`——能够解释观察到的行为，但仍存在其他可能解释。
- `【建议设计】`——建议采用的未来状态。
- `【尚未确认】`——证据缺失、模糊或相互矛盾。
- `【证据冲突】`——多个直接信号不一致。

当两个直接证据相互冲突时，必须建立冲突记录：

```text
C01
信号 A：聊天中显示“已生成”
信号 B：资产库为空
信号 C：预览提示素材不完整
结论：展示状态或状态语义存在冲突；尚不能证明底层存储失败
```

不能把相互冲突的证据压缩成一个确定事实。

### 完成信号矩阵

对所有“已生成”或“已完成”分别核对：

| 信号 | 可以确认 | 仍不能确认 |
|---|---|---|
| Agent/产品文字声明 | 产品做出了完成表述 | 资产存在、内容正确 |
| 资产/文件存在 | 有可读取结果对象 | 内容有效、平台权威完成 |
| 内容验证通过 | 结构、字段、引用或执行结果满足检查 | UI 状态、费用和外部副作用已结算 |
| UI/任务状态 Completed | 平台把任务投影为完成 | 外部系统一定成功、内容一定正确 |
| 账单/外部系统状态 | 消耗或现实世界状态已落地 | 其他质量维度 |

如果这些信号不一致，建立 `C##`。例如文件存在但任务仍为 3/4，只能确认资产存在，不能确认整次任务完成。

## 3. 用户层

必须依据当前产品证据回答：

- 目标用户是谁？他们想完成什么任务？
- 用户提供了哪些输入？哪些是必填、可选或长期信息？
- 最早入口是什么？最终可见结果是什么？
- 存在哪些判断节点和确认门？
- 用户在哪里可以继续、修改、换方案、停止或返回？
- 产品如何表达进度、质量、成本和完成状态？
- 行为证据支持哪些情绪或信心变化？
- 哪些阻力来自语义模糊、等待、状态不一致、成本、失败或失去控制？
- 用户不满意或任务失败后，恢复路径是什么？

证据充分时，至少输出：

- 按时间排序的证据表；
- 用户旅程图或决策流程；
- 产品实际表现出的完成条件；
- 最重要的用户体验风险和产品机会。

## 4. 技术层

先分析可观察职责，再判断可能的技术实现：

- 交互界面和应用模块；
- 工作流编排、Agent 交接、用户确认门和状态机；
- 工具/服务边界和异步执行；
- 结果验证、重试、幂等、取消和部分成功；
- 资产持久化、预览/导出和状态投影；
- 身份认证、权限、计费、安全、审计、日志和告警；
- 当前行为所要求的基础设施能力。

除非源代码、配置或官方证据明确证明，否则不能声称产品使用了某种编程语言、数据库、队列、云服务或框架。对于不可见基础设施，使用以下表达结构：

```text
所需能力 → 可选实现 → 建议方案 → 为什么现有实现仍未知
```

## 5. 模型层

先确认产品是否有可见的模型使用证据。如果没有，应保持简短并标记未知，不要强行补出 AI 架构。

模型相关时，检查：

- 模态：文本、图片、视频、音频、向量、重排、分类；
- 角色：规划、生成、抽取、评估、安全、路由；
- 用户可选的模型、版本或参数；
- 自动路由或降级证据；
- 传递给模型的上下文和资产引用；
- 知识检索与 Prompt/模板行为；
- 能力限制：时长、分辨率、输入大小、参考资料、语言；
- 成本、延迟、质量、安全和失败之间的权衡；
- 输出验证和评估；
- 重试、降级或切换模型。

页面存在模型选择器，只能证明用户可以选择模型或版本，不能证明存在动态模型路由。公开的“思考”摘要只能证明产品展示了判断摘要，不能证明读取到了隐藏思维链。

## 6. 数据层

先按语义梳理数据对象，再考虑具体表名：

- 用户、账号、权限、偏好；
- 项目、工作空间、对话；
- 需求、剧本、文档、任务、计划；
- 角色、Agent、运行实例、工具调用；
- 资产及资产版本；
- 上游与下游产物之间的引用；
- 确认和审批记录；
- 任务、工作流和错误状态；
- 模型调用和评估；
- 计费与用量记录；
- 公共知识与用户私有资产。

每个对象应记录：

| 对象 | 生产者 | 消费者 | 读写时机 | 版本/引用行为 | 证据等级 | 证据编号 |
|---|---|---|---|---|---|---|

必须明确检查：

- 稳定 ID 与展示名称/别名；
- 快照引用与实时引用；
- 上游修改是否导致下游失效；
- 多版本和历史记录；
- 只写不读或只读不写的字段；
- 数据保留及项目/租户隔离；
- 聊天、画布、任务、资产和预览之间的状态投影一致性。

## 7. 跨层追踪

至少追踪一条正常路径；如果证据存在，再追踪一条修改路径或失败路径：

| 步骤 | 用户层 | 技术层 | 模型层 | 数据层 | 用户确认 | 证据 |
|---|---|---|---|---|---|---|

跨层追踪应能够回答：

- 用户意图从哪里进入系统？
- 谁或哪个模块决定下一步？
- 调用了什么工具或模型？
- 读取了什么数据和资产引用？
- 写入了什么？这些结果显示在哪里？
- 哪些步骤必须由用户确认？
- 上游修改如何使下游工作失效？
- 失败、中断或状态不一致后会发生什么？
