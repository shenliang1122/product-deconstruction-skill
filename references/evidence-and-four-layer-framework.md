# 证据门槛与四层拆解框架

每次产品拆解都必须读取本参考资料。

## 1. 证据门槛

### 一手证据

可接受的一手证据包括：

- 按时间顺序排列，能够显示控件、消息、状态、资产、错误和结果的完整页面截图或录屏；
- 已获用户授权、可以只读检查的产品网址；
- 原始源代码及相关配置；
- 导出的消息、项目数据、任务记录、日志或资产元数据；
- 来源可见的生成结果文件；
- 与观察行为直接对应的官方文档。

以前的分析总结、文件名、图片说明、营销文案和个人记忆都属于二手证据。它们只能用于定位一手证据，不能单独用于确认事实。

### 证据就绪度维度

使用定性判断，不使用数字评分：

| 维度 | 达到就绪的条件 | 常见缺口 |
|---|---|---|
| 范围 | 目标产品/功能/Agent 及期望深度明确 | 产品名仍是占位符，或只说“全部分析” |
| 覆盖 | 入口、主流程、决策、结果和至少一次状态变化可见 | 只有宣传首页或一张孤立的最终结果截图 |
| 时间顺序 | 可以从最早到最晚还原过程 | 截图没有顺序，或缺少中间状态 |
| 可读性 | 页面原文、控件、资产和错误能够辨认 | 截图被裁剪、模糊或只有缩略图 |
| 结果验证 | 可以在界面、资产或代码中核对产品声称的输出 | Agent 说“完成”，但没有结果承载界面 |
| 状态覆盖 | 聊天、画布、任务、资产、预览或同类状态界面可见 | 多界面工作流只展示了其中一个界面 |
| 来源 | 证据来源、时间或顺序已知 | 文件被重命名，且文件名与内容冲突 |

### 门槛判断

- **不充分：** 没有一手证据、证据不可读或目标不明确。索取缺失证据并停止。
- **部分充分：** 足以回答一个有限问题，但不足以还原完整架构。只分析被支持的范围，并先列出证据缺口。
- **充分：** 足以追踪用户输入、系统判断、执行、输出和状态变化，覆盖当前请求范围。

证据是否充分取决于问题本身。一张截图可以证明某个按钮的名称，但不能证明完整端到端旅程。

### 不同分析模式的最低证据要求

| 模式 | 最低证据 |
|---|---|
| 用户旅程 | 最早输入、所有可见确认/选择步骤、最终结果、失败界面或证据缺口 |
| 单个 Agent | 每次可见出现、触发条件、输入、公开计划、工具/结果痕迹、输出、确认和下游交接 |
| 工具契约 | 调用上下文、参数或选项、成功结果、状态写入；失败和重试只能在真实发生时分析 |
| 架构拆解 | 用户旅程 + Agent/工具/上下文证据 + 模型/配置界面 + 资产/状态/错误界面 |
| 源代码拆解 | 程序入口、核心领域模块、数据模型、外部集成、配置，以及相关测试或日志 |

## 2. 证据纪律

统一使用四类标签：

- `【页面/代码事实】`——可以直接看到或复现。
- `【合理推断】`——能够解释观察到的行为，但仍存在其他可能解释。
- `【建议设计】`——建议采用的未来状态。
- `【尚未确认】`——证据缺失、模糊或相互矛盾。

当两个直接证据相互冲突时，必须建立冲突记录：

```text
C01
信号 A：聊天中显示“已生成”
信号 B：资产库为空
信号 C：预览提示素材不完整
结论：展示状态或状态语义存在冲突；尚不能证明底层存储失败
```

不能把相互冲突的证据压缩成一个确定事实。

## 3. 用户层

必须依据当前产品证据回答：

- 目标用户是谁？他们想完成什么任务？
- 用户提供了哪些输入？哪些是必填、可选或长期信息？
- 最早入口是什么？最终可见结果是什么？
- 存在哪些判断节点和确认门？
- 用户在哪里可以继续、修改、换方案、停止或返回？
- 产品如何表达进度、质量、成本和完成状态？
- 行为证据支持哪些情绪或信心变化？
- 哪些阻力来自语义模糊、等待、状态不一致、成本、失败或失去控制？
- 用户不满意或任务失败后，恢复路径是什么？

证据充分时，至少输出：

- 按时间排序的证据表；
- 用户旅程图或决策流程；
- 产品实际表现出的完成条件；
- 最重要的用户体验风险和产品机会。

## 4. 技术层

先分析可观察职责，再判断可能的技术实现：

- 交互界面和应用模块；
- 工作流编排、Agent 交接、用户确认门和状态机；
- 工具/服务边界和异步执行；
- 结果验证、重试、幂等、取消和部分成功；
- 资产持久化、预览/导出和状态投影；
- 身份认证、权限、计费、安全、审计、日志和告警；
- 当前行为所要求的基础设施能力。

除非源代码、配置或官方证据明确证明，否则不能声称产品使用了某种编程语言、数据库、队列、云服务或框架。对于不可见基础设施，使用以下表达结构：

```text
所需能力 → 可选实现 → 建议方案 → 为什么现有实现仍未知
```

## 5. 模型层

先确认产品是否有可见的模型使用证据。如果没有，应保持简短并标记未知，不要强行补出 AI 架构。

模型相关时，检查：

- 模态：文本、图片、视频、音频、向量、重排、分类；
- 角色：规划、生成、抽取、评估、安全、路由；
- 用户可选的模型、版本或参数；
- 自动路由或降级证据；
- 传递给模型的上下文和资产引用；
- 知识检索与 Prompt/模板行为；
- 能力限制：时长、分辨率、输入大小、参考资料、语言；
- 成本、延迟、质量、安全和失败之间的权衡；
- 输出验证和评估；
- 重试、降级或切换模型。

页面存在模型选择器，只能证明用户可以选择模型或版本，不能证明存在动态模型路由。公开的“思考”摘要只能证明产品展示了判断摘要，不能证明读取到了隐藏思维链。

## 6. 数据层

先按语义梳理数据对象，再考虑具体表名：

- 用户、账号、权限、偏好；
- 项目、工作空间、对话；
- 需求、剧本、文档、任务、计划；
- 角色、Agent、运行实例、工具调用；
- 资产及资产版本；
- 上游与下游产物之间的引用；
- 确认和审批记录；
- 任务、工作流和错误状态；
- 模型调用和评估；
- 计费与用量记录；
- 公共知识与用户私有资产。

每个对象应记录：

| 对象 | 生产者 | 消费者 | 读写时机 | 版本/引用行为 | 证据等级 | 证据编号 |
|---|---|---|---|---|---|---|

必须明确检查：

- 稳定 ID 与展示名称/别名；
- 快照引用与实时引用；
- 上游修改是否导致下游失效；
- 多版本和历史记录；
- 只写不读或只读不写的字段；
- 数据保留及项目/租户隔离；
- 聊天、画布、任务、资产和预览之间的状态投影一致性。

## 7. 跨层追踪

至少追踪一条正常路径；如果证据存在，再追踪一条修改路径或失败路径：

| 步骤 | 用户层 | 技术层 | 模型层 | 数据层 | 用户确认 | 证据 |
|---|---|---|---|---|---|---|

跨层追踪应能够回答：

- 用户意图从哪里进入系统？
- 谁或哪个模块决定下一步？
- 调用了什么工具或模型？
- 读取了什么数据和资产引用？
- 写入了什么？这些结果显示在哪里？
- 哪些步骤必须由用户确认？
- 上游修改如何使下游工作失效？
- 失败、中断或状态不一致后会发生什么？
